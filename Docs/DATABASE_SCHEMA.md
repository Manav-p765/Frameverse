## 1. Introduction

This document describes the MongoDB database architecture for **Frameverse** — a developer-centric social platform supporting real-time interactions, media sharing, and engagement analytics.

The schema is designed around the following core principles:

- **Flexibility** — Document-oriented structure adapts to evolving content requirements.
- **Performance** — Strategic indexing ensures efficient reads for feed loading, notifications, and analytics.
- **Integrity** — Schema-level validation via Mongoose enforces data consistency at the application layer.

---

## 2. Database Overview

| Property | Value |
|---|---|
| Database | MongoDB Atlas |
| ODM | Mongoose (Node.js) |
| Architecture | Document-oriented, normalized references via `ObjectId` |

Mongoose is used as the Object Data Modeling library to define schemas, enforce validation rules, and manage relationships between collections through `ObjectId` references.

## 4. User Schema

Stores core identity data, authentication credentials, and the user's social graph.

```js
{
  username:   { type: String,  required: true, unique: true },
  email:      { type: String,  required: true, unique: true },
  password:   { type: String,  required: true },               // bcrypt-hashed
  bio:        { type: String,  default: "" },
  profilePic: { type: String,  default: "default.png" },       // URL to profile image
  followers:  [{ type: ObjectId, ref: 'User' }],               // Users following this account
  following:  [{ type: ObjectId, ref: 'User' }],               // Users this account follows
  role:       { type: String,  enum: ['user', 'admin'], default: 'user' },
  isVerified: { type: Boolean, default: false },
  createdAt:  { type: Date,    default: Date.now },
  updatedAt:  { type: Date,    default: Date.now }
}
```

**Notes:**
- `password` is stored as a bcrypt hash and must never be returned in API responses.
- `followers` and `following` are self-referencing arrays that form the platform's social graph.
- `isVerified` indicates whether the user has completed email verification.

## 5. Post Schema

Represents a piece of user-created content, including its associated media, metadata, and high-level engagement counters.

```js
{
  author:       { type: ObjectId, ref: 'User', required: true },
  image:        { type: String,   required: true },                           // URL to media asset
  description:  { type: String,   maxLength: 2200 },
  location:     { type: String },
  postType:     { type: String,   enum: ['manual', 'auto-progress'], default: 'manual' },
  likes:        [{ type: ObjectId, ref: 'User' }],                            // Array of users who liked
  likeCount:    { type: Number,   default: 0 },                               // Denormalized counter
  commentCount: { type: Number,   default: 0 },                               // Denormalized counter
  shares:       { type: Number,   default: 0 },
  tags:         [String],
  createdAt:    { type: Date,     default: Date.now }
}
```

**Notes:**
- `likeCount` and `commentCount` are denormalized counters kept in sync with their respective arrays/collections. This avoids expensive aggregation queries on high-traffic feeds.
- `postType` distinguishes between manually created posts and those generated by automated progress tracking features.
- `tags` supports discoverability and content filtering.

## 6. Comment Schema

Supports threaded discussions on posts. A comment may be a top-level response or a reply to another comment.

```js
{
  postId:          { type: ObjectId, ref: 'Post',    required: true },
  author:          { type: ObjectId, ref: 'User',    required: true },
  content:         { type: String,   required: true, maxLength: 1000 },
  parentCommentId: { type: ObjectId, ref: 'Comment', default: null },  // null = top-level comment
  likes:           [{ type: ObjectId, ref: 'User' }],
  createdAt:       { type: Date,     default: Date.now }
}
```

**Notes:**
- `parentCommentId` enables one level of nested replies. A value of `null` indicates a top-level comment.
- Replies inherit `postId` from their parent, allowing all comments on a post to be retrieved with a single query.

## 7. Notification Schema

Generates real-time alerts to inform users of relevant interactions on their content or profile.

```js
{
  recipient: { type: ObjectId, ref: 'User', required: true },
  sender:    { type: ObjectId, ref: 'User', required: true },
  type:      { type: String,   enum: ['like', 'comment', 'follow', 'mention'], required: true },
  postId:    { type: ObjectId, ref: 'Post' },   // Optional — not applicable to 'follow' notifications
  isRead:    { type: Boolean,  default: false },
  createdAt: { type: Date,     default: Date.now }
}
```

**Notes:**
- `postId` is optional and only populated for `like`, `comment`, and `mention` notification types.
- `isRead` is used to render unread badge counts in the UI and should be indexed alongside `recipient` for efficient inbox queries.

## 8. Analytics Schema

Captures engagement and reach data for individual posts or platform-wide metrics over time.

```js
{
  postId:      { type: ObjectId, ref: 'Post' },  // Optional — omit for platform-wide metrics
  userId:      { type: ObjectId, ref: 'User' },
  views:       { type: Number,   default: 0 },
  engagements: { type: Number,   default: 0 },   // Computed as: likes + comments
  reach:       { type: Number,   default: 0 },   // Estimated unique accounts reached
  timestamp:   { type: Date,     default: Date.now }
}
```

**Notes:**
- Documents can represent either post-level or user-level analytics depending on which fields are populated.
- `engagements` should reflect the sum of `likeCount` and `commentCount` at the time of recording.
- For time-series analysis, query by `userId` or `postId` sorted by `timestamp`.

## 9. Collection Relationships

All inter-collection references use MongoDB `ObjectId` for a normalized data model.

```
User ──────────────── Post
│  (1 : Many)         │
│  author field        │
│                     │
│                     ├──────────── Comment
│                     │  (1 : Many)
│                     │  postId field
│                     │
│                     └──────────── Analytics
│                        (1 : Many)
│                        postId field
│
├──────────── Notification
│  (1 : Many)
│  recipient / sender fields
│
└──────────── User (self-reference)
   (Many : Many)
   followers / following arrays
```

| Relationship | Type | How It's Modeled |
|---|---|---|
| User → Posts | One-to-Many | `author` field on `Post` references `User._id` |
| Post → Comments | One-to-Many | `postId` field on `Comment` references `Post._id` |
| Comment → Replies | One-to-Many (self) | `parentCommentId` on `Comment` references `Comment._id` |
| User → Followers/Following | Many-to-Many (self) | `followers` and `following` arrays on `User` |
| User → Notifications | One-to-Many | `recipient` and `sender` fields reference `User._id` |
| Post → Analytics | One-to-Many | `postId` on `Analytics` references `Post._id` |

## 10. Indexing Strategy

Indexes are applied to fields used in frequent, performance-critical queries. All unique constraints are enforced at the index level.

| Collection | Field(s) | Index Type | Purpose |
|---|---|---|---|
| `users` | `email` | Unique | Authentication lookups |
| `users` | `username` | Unique | Profile resolution, @mention search |
| `posts` | `author` | Standard | Fetching all posts by a user (profile feed) |
| `posts` | `createdAt` | Standard (desc) | Sorting the main feed chronologically |
| `comments` | `postId` | Standard | Retrieving all comments for a given post |
| `notifications` | `recipient`, `isRead` | Compound | Inbox queries filtered by unread status |

> **Recommendation:** As the platform scales, consider adding a **compound index** on `posts (author, createdAt)` to optimize paginated profile feeds, and a **TTL index** on `notifications (createdAt)` to automatically expire old notifications after a defined retention period.
